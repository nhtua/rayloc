# Bounded byte chunk scanning measurements

Measured 2026-10-06 on an AMD Ryzen 9 9950X, Linux 7.1.13-2-Manjaro,
`rustc 1.88.0`, warm filesystem cache. Fixtures were generated by
`scripts/longline_measure.py` as one minified JSON physical line with a single
synthetic AWS-shaped candidate near the midpoint. Every completed scan reported
one finding, the full input byte count, and no leaked credential. Three timed
runs followed one untimed warm run. Peak RSS is the scanner child’s native
`wait4` high-water mark. The full measurements, binary SHA-256 values, and setup
are in [the JSON report](byte-chunk-scanning-results.json).

| Input | Original 1 MiB | Raised 5 MiB | Raised 10 MiB | Bounded chunks |
| ---: | --- | --- | --- | --- |
| 1 MB | 3.77 ms, 265 MB/s, 5,588 KiB | 3.77 ms, 265 MB/s, 5,636 KiB | 3.02 ms, 331 MB/s, 5,596 KiB | 7.74 ms, 129 MB/s, 5,600 KiB |
| 2 MB | exit 2 (cap) | 5.00 ms, 400 MB/s, 6,652 KiB | 5.03 ms, 398 MB/s, 6,796 KiB | 11.74 ms, 170 MB/s, 5,416 KiB |
| 5 MB | exit 2 (cap) | 11.14 ms, 449 MB/s, 9,452 KiB | 10.87 ms, 460 MB/s, 9,428 KiB | 26.79 ms, 187 MB/s, 5,328 KiB |
| 10 MB | exit 2 (cap) | exit 2 (cap) | 20.01 ms, 500 MB/s, 14,296 KiB | 51.07 ms, 196 MB/s, 5,544 KiB |
| 64 MB | exit 2 (cap) | exit 2 (cap) | exit 2 (cap) | 315.02 ms, 203 MB/s, 5,364 KiB |
| 256 MB | exit 2 (cap) | exit 2 (cap) | exit 2 (cap) | 1,244.35 ms, 206 MB/s, 5,288 KiB |

The byte-chunk implementation completed all tested sizes with peak RSS staying
within 312 KiB across the 1–256 MB fixtures. On this particular sparse JSON
workload, whole-line scans were about 1.3–2.5 times faster where their cap
allowed a complete scan, and their peak RSS grew with line size. Raising the cap
therefore works as an interim compatibility choice for files known to stay below
that cap, but it retains input-sized memory growth and still rejects larger
lines. The 1 MiB baseline’s exit 2 results are incomplete scans and are not
throughput comparisons.

The separate ordinary engine benchmark remained within the 10% median runtime
gate: baseline `cargo bench --locked --bench engine` reported 3.182 ms median
(85.61 MB/s, 40 samples); the chunk worktree reported 3.333 ms (81.71 MB/s, 40
samples), a 4.74% median slowdown in this paired run. However, the ordinary
scope benchmark exceeded the 10% gate. With 256 files of 16,418 bytes each and
one worker, baseline runs measured 41.60 ms and 40.36 ms medians; chunk-worktree
runs measured 48.31 ms and 48.85 ms, or 16.1–21.0% slower across these paired
runs. This scope regression remains unresolved and requires optimization or a
documented adjustment before the performance gate can be considered satisfied.
The `engine` fixture consists of 272,384 bytes of short records and is not a
substitute for a directory-scope benchmark.

## Reproduction

The baseline was built from `c4c8a5f`. Experimental 5/10 MiB binaries used that
same source, changing both `src/scanner/engine.rs::MAX_LINE_BYTES` and
`src/scanner/diff.rs::MAX_RECORD_BYTES` to the corresponding cap. Each `sed`
replacement below changes the `1024 * 1024` expression in both files. The chunk
binary was built from the active, uncommitted implementation worktree based on
the same revision; its exact binary hash is in the JSON report. All used locked
release builds in separate target directories. The chunk binary used branch
HEAD `03bba55b126940b971eeb402556d340ce478f841` plus uncommitted implementation
changes. The measured direct-file workloads exercise the physical-line cap;
they do not exercise Git patch record limits.

```sh
git worktree add /tmp/rayloc-byte-base c4c8a5f
cd /tmp/rayloc-byte-base
CARGO_TARGET_DIR=/tmp/rayloc-target-base-clean cargo build --locked --release
git worktree add /tmp/rayloc-byte-cap5 c4c8a5f
cd /tmp/rayloc-byte-cap5
sed -i 's/1024 \* 1024/5 * 1024 * 1024/g' src/scanner/engine.rs src/scanner/diff.rs
CARGO_TARGET_DIR=/tmp/rayloc-target-cap5 cargo build --locked --release
git worktree add /tmp/rayloc-byte-cap10 c4c8a5f
cd /tmp/rayloc-byte-cap10
sed -i 's/1024 \* 1024/10 * 1024 * 1024/g' src/scanner/engine.rs src/scanner/diff.rs
CARGO_TARGET_DIR=/tmp/rayloc-target-cap10 cargo build --locked --release
CARGO_TARGET_DIR=/tmp/rayloc-target-chunk cargo build --locked --release
PYTHONDONTWRITEBYTECODE=1 python3 scripts/longline_measure.py \
  --binary base=/tmp/rayloc-target-base-clean/release/rayloc \
  --binary cap5=/tmp/rayloc-target-cap5/release/rayloc \
  --binary cap10=/tmp/rayloc-target-cap10/release/rayloc \
  --binary chunk=/tmp/rayloc-target-chunk/release/rayloc \
  --sizes-mib 1 2 5 10 64 256 --samples 3 \
  --output docs/research/byte-chunk-scanning-results.json
```

This is a small synthetic benchmark, not a representative corpus study. It does
not measure dense findings, trailing ignore directives, custom regexes,
adversarial regex execution, staged/diff acquisition, forced reader fragment
sizes, or 1 GiB input. Three runs support a coarse median only. Capacity bounds
are enforced and tested by the implementation; this process-level RSS sample
does not directly inspect allocator capacity. Re-run on the target deployment
host before making machine-specific performance claims.
